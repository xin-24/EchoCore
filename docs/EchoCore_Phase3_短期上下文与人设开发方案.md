# EchoCore 第三阶段开发方案

Phase 3：短期上下文与人设
版本：v0.1（规划稿）
状态：Step 1 契约已定稿；其余步骤待 Phase 2 验收完成后实施

## 1. 阶段目标

让开启 AI 的群聊可以结合近期对话自然接话，能区分发言者与引用关系，并按配置保持一致的交流风格。私聊直接发送普通文本即可与 AI 对话；群聊仍由白名单用户用 `/ai on/off` 控制。

阶段完成后，EchoCore 应能在有界的短期消息窗口内回答追问；群聊与私聊、不同群、不同机器人账号之间的消息和配置严格隔离；每轮模型判断和生成使用接收消息时冻结的上下文；群关闭后不再积累或使用旧上下文。

## 2. 开始条件与不包含内容

### 2.1 开始条件

先完成 Phase 2 的关键验收：真实 QQ 群能执行 `/ai on`、普通消息可选择性触发回答、`/ai off` 后停止 AI 回复，且 `/ping`、`/help` 无回归。群回复冷却和判断调用频率控制属于 Phase 2 收尾，应先明确，避免引入历史后扩大模型调用量。私聊普通消息直接进入 AI；群聊仍通过白名单控制的 `/ai on/off` 开启或关闭。

已有自动化测试不替代真实 QQ 验收。若 Phase 2 仍有已知缺陷，先记录并决定是否阻塞 Phase 3。

### 2.2 本阶段不包含

- SQLite、跨重启恢复或长期记忆。
- Embedding、RAG、摘要模型或向量数据库。
- 管理后台、Web 配置页面和聊天记录浏览器。
- 联网搜索、工具调用、图片或语音理解。
- 新增 `/ask` 命令或为私聊消息添加命令前缀要求；私聊直接文本对话遵循当前既定行为。
- 好感度、复杂队列和持久化任务。

本阶段短期上下文默认仅在内存中，服务重启后清空。

## 2.3 Step 1 契约决策（已定稿）

以下规则从本方案定稿开始作为 Phase 3 后续实现的基准。若实现中发现必须改变其中某项，应先更新本节及验收项，再实现，不在代码里悄悄采用不同规则。

| 决策项 | 定稿规则 |
| --- | --- |
| 存储 | 只存内存，不写磁盘、数据库、常规日志或模型错误日志；服务退出后全部清空 |
| 开启群 | 收到白名单用户的 `/ai on` 后创建新的空上下文；该命令本身不入历史 |
| 关闭群 | `/ai off` 先使本次开启周期失效，再停止收录并清空该群上下文；取消该周期未完成任务；再次开启从空上下文开始，旧周期的延迟写入必须被拒绝 |
| 忙碌消息 | 不排队、不追加历史、不触发 Decide/Generate；群普通消息静默跳过，群内直接 @ 和私聊消息沿用现有繁忙提示 |
| 普通群消息 | 群已开启且模型 Provider 已启用时，非命令文本进入历史；即使 Decide 忽略，也保留到短期窗口供后续消息参考 |
| 群直接 @ | 开启群内的真实 @ 消息进入历史并直接 Generate，不调用 Decide |
| 私聊消息 | 普通私聊文本直接进入该用户上下文并 Generate；已注册命令优先，未知斜杠命令（含旧 `/ask`）忽略 |
| 私聊模型关闭 | Provider 为 `disabled` 时不创建、不收录私聊上下文，也不回复 |
| 机器人回复 | 仅 OneBot Action 响应 `status=ok` 且 `retcode=0` 后追加 assistant 消息；失败、超时、断开、结果未知均不追加、不重试 |
| 群隔离 | 群 A 与群 B 永不共享；同群成员共享一个群上下文 |
| 私聊隔离 | 以平台、机器人账号、私聊类型和对方用户 ID 隔离；不同用户间不共享 |
| 上下文过期 | 会话闲置 30 分钟清空；清理任务最多每分钟检查一次 |
| 淘汰 | 每会话最多存 100 条；全服务最多 5,000 条、500 个会话；容量不足时按最久未活动会话优先淘汰，不淘汰仍有在途任务的会话；若没有可淘汰会话，新会话仅处理当前输入，不保存上下文 |
| 模型历史 | 最多取最近 20 条历史，并受 8,000 Unicode 字符总预算约束；预算包含历史、当前输入和格式化后的发言者／引用信息，不含系统提示及模型输出 |
| 单条消息 | 历史正文最多 2,000 Unicode 字符；超限项在入库前截断并标记截断，不增加模型输入上限 |
| 当前输入 | 继续服从现有 `ECHOCORE_LLM_MAX_INPUT_CHARS`；当前输入和历史合并后再次执行总预算限制，过长时先从最旧历史开始丢弃 |
| 顺序 | 每条接收消息分配进程内单调递增序号；模型快照按该序号排序，不依赖秒级平台时间决定先后 |
| 重复消息 | 会话内存在非空 OneBot `message_id` 时去重；没有 ID 时按新消息处理 |
| 用户资料 | 内存记录发送者 ID 以区分成员，并保留当前 OneBot 提供的昵称／群名片；不缓存性别、年龄、地区、等级等资料；投影给模型时不发送 QQ ID |
| 引用 | 只保留引用目标消息 ID；若目标正文仍在本会话窗口，可在快照中关联，否则只向模型说明引用内容不可用，不猜测正文 |
| 同群关闭与私聊 | 群开关只控制群上下文，不影响私聊；私聊通过直接发送普通文本开始交流 |
| 原始事件日志 | Phase 3 接入上下文前，DEBUG 原始 OneBot 日志须默认移除 `raw_message` 和文本 segment 正文；不得因为开启 DEBUG 而旁路上下文隐私策略 |

“忙碌消息不入历史”的目的，是确保未被模型处理的消息不会被误当作机器人已理解的上下文。本阶段不创建待处理队列；用户可以在当前任务结束后重发。

### 消息契约

会话键由以下字段构成，均为必填：

```text
Platform, SelfID, ConversationType, ConversationID
```

`ConversationType` 取 `group` 或 `private`。群聊的 `ConversationID` 是 `GroupID`；私聊为对方 `UserID`。任何必填标识缺失时，消息不进入上下文 Store。

上下文消息结构固定包含：

| 字段 | 类型／约束 |
| --- | --- |
| `Sequence` | `uint64`，进程内单调递增 |
| `MessageID` | 字符串，可空；非空时用于会话内去重 |
| `Role` | `user` 或 `assistant` |
| `SenderID` | 字符串；assistant 使用机器人账号 ID |
| `DisplayName` | 字符串，可空；OneBot 群名片优先，否则昵称；作为不可信普通文本 |
| `Text` | 已归一化文本，按 2,000 Unicode 字符限制 |
| `Timestamp` | `time.Time`；异常／缺失的平台时间使用本地接收时间 |
| `ReplyToMessageID` | 字符串，可空；不凭空补全引用正文 |
| `Truncated` | `bool`，标记入库前正文已截断 |

Store 按会话键和开启周期维护不可变快照。群开启周期由单调递增的本地 generation 标识；关闭时先使 generation 失效，任何迟到的旧任务回写都必须被拒绝。传给 `llm.Input.History` 时，将发言者显示名或稳定的会话内代称、可用引用标识格式化为 user 内容的一部分；不把昵称提升为 system/developer 角色，也不发送 QQ ID。当前消息仍单独放在 `llm.Input.Text`，`History` 不重复包含当前消息。

## 3. 当前代码边界与改造方向

当前 `message.IncomingMessage` 只有平台、账号、用户、群、消息 ID、正文、群聊和 @ 标记；OneBot `Event` 已包含事件秒级时间和发送者资料。Adapter 当前只提取文本和 @。

`llm.Input` 已有 `Text` 和 `History []llm.Message`，但历史只有 `Role` 与 `Text`，且 Executor 当前只传 `Text`。`Router` 与 `Executor` 通过 `message.Work` 连接；群的开启周期在 `group.StateStore` 中由 `Session` 表示，关闭时会取消任务。

因此本阶段的主要工作是增加带来源信息的统一消息记录、短期上下文存储与快照，并把快照注入现有 Decide / Generate 路径。OneBot 协议类型不应泄漏到 LLM 或上下文存储层。

建议的职责边界：

| 模块 | 职责 |
| --- | --- |
| OneBot Adapter | 补充消息时间、发送者昵称／群名片、回复目标等平台数据，并转换为平台无关字段 |
| Conversation / Context | 生成会话键、维护有界消息窗口、裁剪历史、产生不可变快照、执行关闭清理 |
| Router | 接收当前消息及快照；在普通群消息时将有限历史交给 Decide |
| Executor | 对直接 @、私聊普通消息跳过 Decide；对需要生成的任务使用同一快照和当前输入 |
| Action Sender | 仅在 OneBot 发送成功后通知上下文记录机器人回复 |
| Persona 配置 | 提供经过校验的系统提示和简单风格配置；不含密钥或平台数据 |

## 4. 会话身份与消息数据

### 4.1 会话键

会话键须包含平台、机器人账号、会话类型和目标 ID：

```text
platform / self_id / conversation_type / conversation_id
```

- 群聊的 `conversation_id` 为 `group_id`，群内所有成员共享群上下文。
- 私聊的 `conversation_id` 为对方 `user_id`，不同用户之间隔离。
- 私聊普通文本直接进入 AI 候选并生成回答；不经过群聊 Decide。已注册的确定性命令仍优先处理，未知斜杠命令（包括已取消的 `/ask`）忽略。
- 缺失关键标识时拒绝进入有状态 AI 上下文，不以空字符串构造共享会话。

会话键不能只用群 ID，否则未来多 QQ 账号或多平台时可能串数据；不能用用户 ID 作为群会话键，否则同群多人看不到共同讨论上下文。

### 4.2 统一消息记录

建议新增平台无关的上下文消息结构，至少包含：

| 字段 | 用途 |
| --- | --- |
| 会话键 | 确保隔离 |
| 消息 ID | 标识来源消息；无效或缺失时允许为空 |
| 发送者 ID、显示名 | 让模型知道群里是谁在发言；显示名是非可信用户数据 |
| 角色 | `user` 或 `assistant` |
| 正文 | 当前阶段仅记录经过 Adapter 转换的文本 |
| 消息时间 | 根据 OneBot 时间记录，校验异常值并避免不合理顺序 |
| 引用目标 | 有效时关联被引用的消息 ID；未知消息保留引用 ID，不猜测内容 |
| 本地接收顺序 | 在单个进程中生成，处理时间相同或时间异常时仍有稳定顺序 |

上下文消息可以扩展 `llm.Message`，或由 Context 层投影成 `llm.Message`。建议不要让 LLM 契约直接依赖 OneBot `Event`。实现时为角色、发送者和引用关系采用稳定的格式化方式，避免拼接成含糊的纯文本。

### 4.3 消息收录规则

群聊：

- 仅当该群 AI 已开启时收录普通文本与真实 @ 机器人文本。
- 先做自身消息、空内容、已识别命令、未知斜杠命令和超长输入过滤。
- 命令本身不进入 AI 对话历史，避免 `/ai on/off`、`/ping`、`/help` 污染聊天上下文。
- Router 判断为 ignore 的普通群消息仍可留在短期历史，以便下一条消息引用上下文；遵循长度、TTL 和窗口上限。
- 未开启群、关闭后收到的消息、自身事件、纯图片／不支持内容不进入 AI 历史。

私聊：

- 私聊普通文本进入对应用户的短期上下文并直接生成回答；同一私聊后续消息可以接续历史。
- 不保存已取消的 `/ask` 命令；未注册的斜杠命令继续忽略。

机器人回复：

- 只有 OneBot 返回成功响应后，才将 assistant 回复写入历史。
- 模型生成成功但 OneBot 发送失败、超时或连接断开，不写入已发送历史。
- 发送结果未知（超时但 NapCat 可能已执行）时不自动重试，也不把该回复标为确认成功；日志需能区分发送失败或结果未知。
- 发送成功后写入回复文本和关联上下文。OneBot 响应确实提供机器人消息 ID 时保存，否则为空。

## 5. 生命周期、顺序与固定快照

### 5.1 开启与关闭

- 群开启周期创建新的空上下文；服务重启亦为空。
- 群关闭时先阻止旧周期追加，再取消该周期任务并清空该群短期上下文，避免重新开启后复用旧对话。
- 关闭群后不再记录新消息；与当前发送 Guard 一致，未写入 NapCat 的旧回复不发送。
- 私聊上下文不受群开关影响，但受自己的 TTL 和内存限制。
- 需要确保群状态和 Context 生命周期的变更顺序明确，避免关闭过程中又有消息写入旧窗口。

### 5.2 快照时序

消息按 WebSocket 接收顺序进行低成本路由及上下文更新。为一条 AI 候选建立任务时，原子地完成“读取已有历史、加入当前入站消息、生成快照”，再异步调用模型。`llm.Input.History` 不得再次包含 `Input.Text` 当前消息。

普通群消息的 Decide 和后续 Generate 使用完全相同的快照与当前输入；直接 @ 及私聊普通消息跳过 Decide，但 Generate 使用该消息创建的快照。后到消息可以进入会话最新窗口，但不能修改已发给模型的快照。

如果正在运行的任务尚未完成，新消息严格遵循已定稿的忙碌规则：不排队、不入历史、不调用模型。群普通消息静默跳过；群内直接 @ 和私聊消息返回当前繁忙提示。用户需在任务结束后重发，避免后续模型误认为它已处理这条消息。

机器人回复仅在 Action 成功确认时追加。它在确认时取得新的本地接收序号，排列在确认前收到的用户消息之后；若 Action 响应失败、超时或断开，不写入 assistant 记录。快照生成使用本地单调序号排序，避免只靠 OneBot 秒级时间造成顺序不稳定。

## 6. 窗口上限与过期策略

第一版只做裁剪和 TTL，不做自动摘要。以下限额已在 Step 1 定稿，作为初次实现默认值：

| 参数 | 定稿默认值 | 说明 |
| --- | --- | --- |
| 每会话保存消息数 | 最近 100 条 | 包含符合收录规则的用户消息及确认发送成功的机器人回复 |
| 上下文交给模型的消息数 | 最近 20 条 | 超过总字符预算时继续从最旧历史裁剪 |
| 会话空闲 TTL | 30 分钟 | 清理每分钟最多执行一次；超时清空窗口 |
| 单条历史正文 | 最多 2,000 Unicode 字符 | 超限入库前截断并标记 |
| 全服务上下文上限 | 5,000 条、500 个会话 | 淘汰最久未活动且没有在途任务的会话 |
| 总输入字符预算 | 8,000 Unicode 字符 | 包含当前输入、历史正文及发言者／引用格式；不含系统提示与输出 |

这些是第三阶段首版的实现默认值，不代表已经写入当前运行配置。若暴露为环境变量，在 `internal/config` 定义默认值和边界；否则集中放在 Context 配置结构中，不散落硬编码。预算单位是 Unicode 字符，不声称与 token 精确等价；模型服务没有统一 tokenizer，因此字符预算是稳定的本地保护上限。

全服务达到上限时应采取可预测的淘汰策略并记录计数，不可无限分配内存。若当时所有会话都有在途任务，新会话仅用当前输入完成一次处理，不创建历史记录。消息或会话清理不能阻塞 WebSocket 收包。

## 7. 人设与模型参数

### 7.1 人设第一版范围

提供默认 EchoCore 人设，并允许通过受校验配置调整：

- 机器人名称／称呼。
- 回复风格（如简洁、友善、自然）。
- 群聊回复长度偏好。
- 基本行为边界（不冒充真人、不声称执行未完成操作、不确定时承认不确定）。

初版使用进程级配置，建议环境变量或当前统一配置结构；不做管理后台和每群持久化人设编辑。角色提示经长度上限和空值检查。配置变化的生效时机需明确：首版重启生效，避免同一会话出现难以复现的提示词突变。

群消息、昵称、引用内容都属于不可信输入，必须与系统人设分隔。人设要求模型把消息视为对话内容，不能遵从它们修改系统规则或执行外部动作。

### 7.2 判断与回复模型

当前 `llm.Client` 同时实现 `Decider` 和 `Generator`，单一 HTTP Client 将 Decide 与 Generate 发往同一配置模型。先保持此默认行为，再通过两个可选角色配置支持分离：

- `router`：群普通消息参与判断。
- `executor`：群直接 @ 与通过判断后的回答生成；私聊普通文本也使用此角色。
- 未配置 router 时复用 executor；未配置 executor 时按当前 disabled 规则处理。
- 两者可配置不同 Provider、Base URL、模型和 API Key；密钥继续仅从安全配置来源读取，绝不进入普通日志。
- 各角色独立超时和最大输出限制，仍受服务级总并发约束；Router 不应绕过群冷却或并发预算。
- Provider 的思考／推理参数必须按该 Provider 支持情况显式配置；无支持或无返回字段时显示“未知／不支持”，不得从回答风格推断已启用深度思考。

若角色拆分会显著扩大当前范围，可将其单独放在 Phase 3 的后半步；短期历史和默认人设不应依赖先完成双 Provider。

## 8. 建议开发步骤

| Step | 任务 | 主要交付 | 完成标准 |

## 9. 自动测试设计

下列测试是实施计划的一部分，执行时按项目现有 Go 测试方式加入单元及集成测试：

### Context Store

- 群 A 与群 B 完全隔离；同群不同用户共享上下文。
- 私聊按机器人账号和用户隔离；私聊与同 ID 群会话不冲突。
- 自身、命令、未开启群消息不写入。
- ignore 普通消息可被后续快照引用；直接 @ 可看到先前消息。
- 当前消息不在 `History` 中重复出现。
- 快照创建后，后续追加或清理不会改变原快照。
- 按消息数、正文长度、总服务容量裁剪；TTL 到期清理。
- 同一时间戳按接收序号稳定排序。
- 关闭群清空旧周期；重新打开得到空窗口。
- 并发追加、快照与清理通过 `go test -race`。

### 模型与发送流程

- Decide 与 Generate 收到同一历史快照。
- 有效 ignore 不调用 Generate；直接 @ 与私聊普通文本跳过 Decide；旧 `/ask` 命令按未知命令忽略。
- 生成失败、空回复、超时、取消不写 assistant 历史。
- OneBot 成功响应才回写 assistant；失败与响应超时不回写。
- 后续任务能够看到已经成功发送的机器人回复。
- 群关闭期间不继续记录旧周期消息或发送旧回复。
- 不改变 `/ping`、`/help`、`/ai on/off` 原有处理。

## 10. QQ 手动验收

使用专用小群和低流量时段，确认模型服务配置有效。每项逐个执行：

1. 重启服务，在群 A 开启 AI；确认群 B 默认关闭。
2. 在 A 依次发送两个相关问题，例如“Go 的 goroutine 是什么？”再发“那它和线程有什么区别？”，检查第二条能利用第一条。
3. 由群成员甲发送一个话题，成员乙追问“刚才说的这个呢？”，确认模型能看到发送者区分及近期消息。
4. 引用一条较早消息提问，确认能识别引用目标；若引用消息已不在窗口，只能看到引用标识，不编造被引用内容。
5. 在 A 发送无关闲聊，确认它被后续历史看到，但 Router 仍可选择忽略，不强迫逐条回答。
6. A 中确认发送一条回复，下一条追问能引用机器人实际回复。
7. 模拟模型错误或关闭 OneBot 发送，确认失败的机器人回答不进入历史。
8. 关闭 A，再开启 A；确认旧上下文已清空。B 的状态和上下文不受影响。
9. 等待 TTL 或通过可控测试时钟验证到期清空；确认大量消息后内存窗口始终受限。
10. 私聊直接发送普通文本交流，同一用户的后续消息可接续历史，另一用户不可见；未知斜杠命令仍忽略。
11. 重启 Go；所有短期历史清空，群 AI 仍默认关闭。
12. 回归 `/ping`、`/help`、权限拒绝、忙碌提示和群关闭取消。

## 11. 运行保护与隐私

- 不记录完整聊天历史到日志。现有开发 DEBUG 原始 OneBot 帧包含正文；Phase 3 接入上下文前，必须默认脱敏 `raw_message` 与文本 segment，避免 DEBUG 日志旁路内存保留策略。
- 显示名、群名片和聊天正文都是用户提供数据；不执行消息中的指令，不将昵称直接拼成 system 角色。
- 短期记录默认仅内存；关闭群即清除，TTL 与全局容量双重限制，进程退出自然清空。
- 只向 Provider 发送当前轮所需最小历史；私聊数据绝不发送到群会话，群 A 绝不发送到群 B。
- API Key、认证头和 Provider 原始错误正文不能写入日志。
- 用户修改配置与人设的后台能力属于后续阶段；本阶段配置由可信部署者设置。
